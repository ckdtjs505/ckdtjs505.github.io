# 블로그 글쓰기 (Sonia.dev)

이 블로그는 "라이브 스트리밍 웹 플레이어를 만드는 프론트엔드 개발자가 부딪힌 문제와 풀어낸 과정"을 기록한다. 글을 쓰기 전에 이 문서의 규칙을 따른다. 기준 글은 `_posts/cef_troubleshooting.md`다. 구조나 문체가 애매하면 이 글을 먼저 읽고 맞춘다.

## 1. 시작: 무엇을 쓸지 확인

사용자에게 받은 주제나 메모에서 아래를 먼저 정한다. 빠진 게 있으면 **한 번에 모아서** 묻는다.

- **실제로 겪은 일인가?** 이 블로그의 강점은 직접 겪은 장애·실험·결정이다. 상황, 원인, 버린 대안, 결과(가능하면 숫자)를 사용자에게서 받는다. 경험이 없는 부분을 지어내지 않는다. 비어 있으면 `<!-- 수치 보강: ... -->` 주석으로 자리만 남긴다.
- **누가 무엇을 검색해서 이 글에 오나?** 한국어 검색어 1~2개를 정한다. 예: "CEF 창 닫힘 API 요청 누락", "pnpm 하드 링크 구조".
- **기존 글과 겹치지 않나?** `_posts/`의 제목·summary를 훑어서 같은 검색어를 노리는 글이 있으면 사용자에게 알린다. 겹치면 새 글 대신 기존 글 보강을 제안한다.

검색어와 개요를 더 깊게 잡아야 하면 `/seo content-brief <주제>`를 먼저 돌려도 된다.

## 2. 파일과 front matter

- 위치: `_posts/<slug>.md`
- **slug는 짧은 영어 소문자와 `-`만 쓴다.** 예: `cef-remote-debugging`. 한글이나 날짜 접두사는 쓰지 않는다. 파일 이름이 그대로 URL이 되고, GitHub Pages는 리다이렉트를 못 하므로 **올린 뒤에는 바꾸지 않는다.**

```yaml
---
layout: post
title: '<검색어가 들어간 구체적인 제목>'
series: '<시리즈 이름, 있을 때만>'
date: <YYYY-MM-DD>
tags: [<태그1>, <태그2>]
comments: true
share: true
related: false
draft: true
summary: <아래 규칙대로 1~2문장>
---
```

- **title**: 검색어를 앞쪽에 넣는다. 질문형이나 "A: B" 형태가 좋다. `[pnpm]` 같은 대괄호 접두사는 쓰지 않는다.
  - 좋음: `CEF 창을 닫으면 API 요청이 사라지는 이유: 모달 종료 Race Condition 트러블슈팅`
  - 나쁨: `[CEF] 트러블슈팅 기록`
- **summary**: 검색 결과·공유 카드·JSON-LD 설명으로 그대로 쓰인다. **핵심 답을 첫 문장에** 넣고, 검색어를 자연스럽게 포함한다. 제목을 반복하지 않는다. 120~200자 정도.
- **series**: 기존 시리즈에 맞으면 같은 이름을 정확히 쓴다. 현재 시리즈: `임베디드 브라우저`, `pnpm 아키텍처`, `Core JS`, `Development Tip`, `초보를 위한 React`, `프로그래머스 알고리즘`. 새 시리즈는 같은 주제로 글이 2개 이상 될 때만 만든다.
- **tags**: 먼저 `grep -h "^tags:" -A6 _posts/*.md`로 기존 태그를 확인하고 있는 이름을 쓴다. 대소문자·한영이 다른 중복 태그(`Refactoring`/`리팩터링`)를 새로 만들지 않는다. 2~5개.
- **draft: true**로 시작한다. 공개할 때 `false`로 바꾸거나 줄을 지운다.
- **featured: true**는 사용자가 대표 글로 올리라고 할 때만 넣는다.
- **modified**: 이미 공개된 글을 크게 고칠 때 `modified: <YYYY-MM-DD>`를 추가한다. 사이트맵과 JSON-LD의 수정일로 쓰인다.

## 3. 본문 구조

```markdown
## TL;DR

- 무엇을 했고 / 무엇이 문제였고 / 어떻게 풀었는지 2~4줄

## <질문형 소제목: 검색어가 들어간 질문>

<첫 1~2문장에 질문에 대한 답을 바로 쓴다. 이 문장만 떼어 읽어도 답이 되게.>

<그 다음에 설명, 코드, 표, 다이어그램>

## <질문형 소제목>
...

## 검토한 대안   ← 트러블슈팅·설계 글이면 꼭
### 1안: ... (버림)
왜 버렸는지

## 결과 / 회고

## 참고
- [문서 제목](URL)
```

규칙:

- **본문에 `#`(H1)을 쓰지 않는다.** 제목은 front matter의 title이 H1으로 나간다. 본문은 `##`부터.
- **소제목은 질문형으로.** "목표/기억하기/내용/느낀점/결론" 템플릿은 쓰지 않는다. 독자가 실제로 검색할 문장으로 쓴다.
  - 좋음: `## pnpm의 하드 링크는 왜 일반 파일처럼 보이나요?`
  - 나쁨: `## 내부 메커니즘`
- **질문 바로 아래 1~2문장에 답.** 주어와 서술어가 있는 완전한 문장으로. 명사로 끝나는 메모식 불릿("...하는 원리", "...가능")만 나열하지 않는다.
- **직접 겪은 맥락을 넣는다.** 상황, 왜 그 선택을 했는지, 무엇을 버렸는지, 수치. 교과서 정의만 있는 글은 이 블로그에서 약한 글이다.
- **다이어그램**은 ` ```mermaid ` 코드 블록을 쓸 수 있다(사이트에서 렌더링됨). 단순 구조는 ` ```text ` 블록도 괜찮다.
- **코드 블록**에는 언어를 붙이고, 실제로 돌아가는 코드만 쓴다. 예: Node.js는 `~`를 홈으로 바꾸지 않으니 `os.homedir()`을 쓴다.
- **같은 시리즈·관련 글은 본문에서 링크한다.** `[글 제목](/posts/<slug>)`. 새 글이 나오면 관련된 기존 글에서도 새 글로 링크를 하나 거는 걸 제안한다.

## 4. 문체

- `~다`체 평서문. (기준: cef_troubleshooting.md)
- 한 문장에 한 가지. 길어지면 나눈다.
- 영어 용어는 처음 나올 때 `한글(English)`로 한 번 풀고 그 뒤로는 편한 쪽으로.
- AI가 쓴 티가 나는 표현을 피한다: "~에 대해 알아보겠습니다", "결론적으로", "다양한", "효율적으로 극대화", 과한 볼드와 이모지.

## 5. 보안·공개 범위 (공개 전에 반드시)

- **회사명, 서비스명, 사내 티켓 접두사, 내부 도메인·경로를 지운다.** 예: 티켓 번호는 `PROJ-101`처럼 일반화한다.
- 취약점·장애 글은 이미 고쳐졌는지, 공개해도 되는지 사용자에게 확인한다. 토큰 형식이나 우회 방법처럼 재현 가능한 세부는 꼭 필요한 만큼만.
- 개인 정보(이메일, 동료 이름)를 넣지 않는다.

## 6. 참고 자료

- 글자로만 적지 않고 **링크를 단다.** 가능하면 공식 문서(MDN, Chrome Docs, pnpm.io, RFC 등).
- 링크는 `curl -sL -o /dev/null -w "%{http_code}" <URL>`로 200인지 확인한다. 깨진 링크는 넣지 않는다.

## 7. 점검

초안을 쓴 뒤 아래를 확인하고, 걸리는 게 있으면 고친다.

- [ ] title·summary에 검색어가 들어갔다
- [ ] 본문에 `# `로 시작하는 줄이 없다 (코드 블록 안의 주석은 괜찮음)
- [ ] 소제목이 질문형이고, 각 질문 바로 아래 1~2문장에 답이 있다
- [ ] 직접 겪은 맥락(상황·이유·버린 대안·결과)이 있다. 없으면 사용자에게 묻거나 주석으로 자리를 남겼다
- [ ] 회사명·서비스명·티켓 접두사가 없다: `grep -n "SOOP" _posts/<slug>.md`
- [ ] 참고 링크가 모두 200이다
- [ ] 관련 글 링크가 1개 이상 있다
- [ ] `npm run build`가 성공한다

더 깊게 보려면 `/seo content`(E-E-A-T, 얇은 글, AI 문체)를 돌린다.

## 8. 브랜치·커밋·PR

- 브랜치: `post/<slug>` (master에서 바로 쓰지 않는다)
- 커밋 메시지: `post: <글 제목 요약> (draft)`, 공개할 때 `post: <요약> 공개 (draft 해제)`
- PR은 사용자가 원할 때만 연다. 병합하면 GitHub Pages로 바로 배포된다.
- 공개 후에는 사용자에게 Search Console의 "URL 검사"로 색인 요청을 하라고 알리고, `/seo page https://ckdtjs505.github.io/posts/<slug>`로 실제 페이지를 확인할 수 있다고 안내한다.

## 사이트가 자동으로 해 주는 것 (손대지 않는다)

글만 올리면 아래는 빌드 때 자동으로 생긴다. front matter만 맞게 쓰면 된다.

- canonical, OG/Twitter 메타, 글별 OG 이미지(`/og/<slug>.png`, 시리즈 이름 포함)
- JSON-LD `BlogPosting`(headline=title, description=summary, datePublished=date, dateModified=modified ?? date)과 `BreadcrumbList`
- 사이트맵, RSS(`/feed.xml`), `llms.txt`, 목차, 읽는 시간, 시리즈 내비게이션, 2년 지난 글 안내
